# Brydon Health Tech Assessment

A simulated multi-tenant EHR ecosystem: independent `single-tenant` instances (one per provider office) each report their patient directory to a shared `tenant-router`, which `patient-portal` queries to provide a unified 2-step login (username, then password, proxied to whichever tenant the username belongs to) across all of them.

## Repo layout

```
single-tenant/client   React 19 + TS + Vite SPA — login, register, welcome (protected)
single-tenant/server   ASP.NET Core 10 minimal API — JWT auth, Postgres, reports users to tenant-router
patient-portal/client  React 19 + TS + Vite SPA — 2-step login (username, then password)
patient-portal/server  ASP.NET Core 10 minimal API — stateless login proxy, no database of its own
tenant-router           ASP.NET Core 10 minimal API — owns the tenant directory (subdomains + hashed usernames), queried by patient-portal

marketing-website/client  React 19 + TS + Vite SPA — placeholder, standalone, not part of the login flow
marketing-website/server  ASP.NET Core 10 minimal API — bare scaffold (health check + CORS only), not part of the login flow

docker-compose.yml               single-tenant + tenant-router Postgres, one instance of each, for normal local dev
docker-compose.multi-tenant.yml  fully containerized: 5 single-tenant pairs + tenant-router + patient-portal, simulating 5 provider offices
db-init/multi-tenant-init.sql    creates the 6 databases the multi-tenant compose stack needs
.env.example                     documents every env var used across all the backend services
```

Each subsystem has its own `CLAUDE.md` with directory-specific detail — this file is cross-cutting architecture and conventions only.

## How the pieces fit together

- **Three backend services, three distinct jobs.** `single-tenant` owns patient data and authentication for one provider office. `tenant-router` owns nothing but the directory — which hashed username belongs to which subdomain, and where that subdomain's server is reachable — with no auth, no client, no login logic of its own. `patient-portal` owns the public-facing 2-step login flow but no data at all: it's a stateless orchestrator that asks tenant-router where to look, then proxies the actual credential check there. This split used to be two services (patient-portal held the directory itself); it was pulled apart so the directory-owning "infrastructure" concern and the login-flow "business logic" concern could evolve independently — see `tenant-router/CLAUDE.md` and `patient-portal/server/CLAUDE.md`.
- **Subdomain-per-deployment.** Each `single-tenant` instance is meant to run on its own subdomain of a shared domain (client and API reverse-proxied to the same origin in production). `SUBDOMAIN` + `APP_DOMAIN` env vars (see `Hosting/DeploymentOrigin.cs`) derive that origin, which is used as the JWT issuer/audience (so a token from one tenant can't validate against another) and folded into the CORS allow-list. Both are optional and fall back to `http://localhost:5251` for local dev.
- **Reporting to tenant-router.** Each `single-tenant` instance hashes its usernames (deterministic HMAC-SHA256, keyed by `TENANT_REPORT_SECRET` — see `Sync/UsernameHasher.cs`, *not* the same hashing as password storage) and `POST`s them to tenant-router's `/api/tenants/report`, authenticated via an `X-Tenant-Report-Key` header compared against the same secret. This happens twice: once at startup (all currently-unreported users) and once per new registration (fire-and-forget, so the HTTP call never blocks the caller) — see `Sync/TenantUserSyncTrigger.cs`, shared by both paths.
- **tenant-router's directory is additive, not a mirror.** `/api/tenants/report` never deletes rows — it inserts `(subdomain, hash)` pairs that don't already exist. A subdomain is auto-created (and its `ServerUrl` kept current) on every report. Normalized: `subdomains` (id, name, server url) + `tenant_usernames` (subdomain_id FK, hash) rather than repeating the subdomain text on every row. Its byte-identical sibling endpoint, `POST /api/tenants/lookup`, is how `patient-portal` resolves a username to candidate tenants — see below.
- **The login is a server-to-server proxy that ends in a redirect, not a hosted session.** patient-portal never stores or verifies passwords — it can't, they live in each tenant's own database — and it never holds a session either: it's a traffic cop, not a place patients stay logged in. It's one endpoint, `POST /api/auth/login`, with an optional `subdomain`: omit it and the server resolves it via a call to tenant-router's `/api/tenants/lookup` (auto-login if the username matches exactly one tenant, `300 Multiple Choices` + the candidate subdomains if it matches more than one — client resubmits with a chosen `subdomain`), or pass a `subdomain` you already know to go straight to that tenant. On any resolved match it forwards the password server-to-server to that tenant's own `/api/auth/login` (via the `ServerUrl` tenant-router reports back) and gets that tenant's JWT — but instead of handing it to the browser to hold, it returns the tenant's `ClientOrigin` too, and `patient-portal/client` does a real cross-origin navigation (`window.location.href`, token in the URL fragment — never a query string, per this project's own safety rules) to `${ClientOrigin}/handoff#token=...`. Each tenant's client owns everything from there — welcome page, logout, whatever it wants — which matters because tenants could plausibly run entirely different client codebases; patient-portal has no business assuming it can host a generic post-login experience for all of them. This is why `single-tenant` reports both `ServerUrl` and `ClientOrigin` alongside its username hashes: `ServerUrl` (`DeploymentOrigin.SelfUrl`) is how *another backend* reaches this tenant's server, `ClientOrigin` (`DeploymentOrigin.ClientOrigin`, sourced from the same `CLIENT_ORIGIN` var already used for CORS) is where a *browser* reaches this tenant's client — distinct audiences, and both diverge from `BaseUrl` (the public JWT-issuer identity) in Docker and local dev, where client/server/public-origin can all be different addresses. Because the redirect only happens *after* a successful password check, this doesn't reopen the username-enumeration concern the next bullet describes — nothing about which tenant(s) a username belongs to is ever revealed without a correct password first.
- **No standalone "does this username exist" endpoint on the public side, and every login failure is indistinguishable.** An earlier version had a separate `/api/auth/identify` on patient-portal — free, unauthenticated, no password required. It was a username-existence oracle and was removed; resolving which tenant(s) a username belongs to now only happens as a side effect of an actual login attempt, which at minimum requires a password. Every failure — no such user, wrong subdomain, wrong password (even the tenant's own genuine `401`, translated on the way back) — returns the exact same `400 BadRequest` with no body from patient-portal. This was tightened once already: a first pass used `401` for the "not found" cases, which itself became a giveaway once distinguishable from the proxied wrong-password case. Note this anti-enumeration caution is specific to patient-portal's *public* endpoint — tenant-router's `/api/tenants/lookup` is server-to-server only (protected by the shared secret, never reachable from a browser) and honestly reports whether a username exists, since hiding that from a caller who already holds the shared secret would protect nothing. See `patient-portal/server`'s `CLAUDE.md` before adding any new failure path there.

## Conventions established across this codebase

- **12-factor config via value objects.** Every piece of environment-specific config (DB credentials, deployment origin, shared secrets) is a `sealed record` with a *private* constructor and a static `FromConfiguration(IConfiguration)` factory that throws `InvalidOperationException` on a missing required var. See `DatabaseCredentials`, `DeploymentOrigin`, `TenantReportSecret`, `TenantRouterReportingOptions`, `TenantRouterOptions` for the pattern. Follow it for any new config.
- **Insert-if-not-exists, not raw SQL.** Preferred pattern: query for existence first, then insert, wrapped in `try/catch` for `DbUpdateException` where `ex.InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation }` — treat the race as a success/no-op rather than propagating a 500. Used for tenant-username inserts, subdomain auto-creation, and username-registration races. Raw SQL (`ON CONFLICT DO NOTHING`) was tried and deliberately reverted in favor of this — it's less atomic under true concurrency but was explicitly preferred to keep the codebase free of raw SQL, and proven safe under concurrent load (10 simultaneous requests, one winner, rest handled cleanly, verified live).
- **EF Core migrations are never trusted blindly.** When a schema change could lose data, EF's auto-scaffolded migration is a starting point, not the final answer — inspect it and hand-edit for backfill logic. We hit this for real with the `NormalizeSubdomains` migration (EF wanted to drop the `Subdomain` text column before the replacement `subdomains` table + FK even existed, defaulting every row to a non-existent id). Always re-run against a database that actually has data in it, not just an empty one.
- **`options.MapInboundClaims = false` is required** in the JWT bearer config (`JwtBearerConfiguration.cs`). Without it, ASP.NET Core silently remaps well-known claim types on the way in (`sub` → `ClaimTypes.NameIdentifier`), so reading raw JWT claim names by their registered names returns null. Cost real debugging time once — don't remove it.
- **Database columns are snake_case, enforced by convention, not by hand.** Both `single-tenant` and `tenant-router` call `.UseSnakeCaseNamingConvention()` (the `EFCore.NamingConventions` package) wherever their DbContext is configured — in `Program.cs` *and* in the design-time `IDesignTimeDbContextFactory`, which must stay in sync or `dotnet ef migrations add` generates against a different model than the app actually runs. C# entity properties stay PascalCase as normal; don't add per-property `.HasColumnName("snake_case_name")` calls to fight the convention, and don't add the naming-convention package to `patient-portal/server` — it has no DbContext, nothing to apply it to. Turning this on for an *already-migrated* database requires a one-time manual fix first: EF's own `__EFMigrationsHistory` tracking table also gets snake_cased (`MigrationId`/`ProductVersion` → `migration_id`/`product_version`), so any existing database needs those two columns renamed by hand (`ALTER TABLE "__EFMigrationsHistory" RENAME COLUMN ...`) before `dotnet ef database update`/the app's own `MigrateAsync()` will run at all — a fresh/empty database doesn't need this, only ones that already have migration history.
- **Nothing blocks on an external HTTP call in the startup or request path.** Calls from `single-tenant` to `tenant-router` go through a `BackgroundService` at startup (`TenantUserSyncHostedService`) or a fire-and-forget trigger with its own DI scope on the request path (`TenantUserSyncTrigger.RunAsync()`, deliberately not awaited by the caller). Never `await` `TenantRouterReportingService` directly inline in `Program.cs` startup or in an endpoint handler.
- **Resilience via Polly — but only for background calls.** `single-tenant`'s HTTP calls to tenant-router are wrapped in retry (3 attempts, exponential backoff) then a circuit breaker (opens after 5 consecutive failures) — see `Sync/TenantRouterRetryPolicy.cs`. Retry wraps the breaker (Microsoft's documented ordering), so retries still respect an open circuit instead of hammering a known-down service. Deliberately *not* used for patient-portal's two outbound calls — the lookup call to tenant-router (`Tenants/TenantRouterClient.cs`) or the login-proxy call to a tenant (`Auth/PatientLoginEndpoints.cs`) — those are both interactive requests with a user waiting, so failing fast (a short timeout, no retry/backoff) is the right behavior, not the slow-and-resilient behavior that's correct for an unattended background sync.
- **Logout is version-based, not a revocation table.** `User.TokenVersion` is embedded in every issued JWT as the `ver` claim; logout increments it (atomic `ExecuteUpdateAsync`), and token validation compares the claim against the current DB value. This was a deliberate replacement for an earlier `revoked_tokens` table design that didn't scale with user count.
- **Vite bakes `VITE_API_BASE_URL` at build time, not runtime.** Matters for Docker: each client image that needs a different backend URl needs its own build with a different `--build-arg`, not a runtime env var substitution.

## Known environment quirks

- **npm/rolldown native-binding bug on this machine.** `npm install` in either client can fail with `Cannot find native binding` (a known npm optional-dependency bug, not specific to this repo). Fix: `npm install @rolldown/binding-darwin-x64@1.2.4 --no-save`. Doesn't happen inside Linux Docker builds — only hits local macOS `npm install`.
- **Ports, local dev (non-Docker, `dotnet run` / `npm run dev`):** single-tenant server `5251`, single-tenant client `5173`, patient-portal server `5009`, patient-portal client `5174`, tenant-router `5236` (per `.claude/launch.json`). single-tenant Postgres `5433`, tenant-router Postgres `5435` (both offset from `5432` to avoid clashing with a locally-installed native Postgres). patient-portal has no Postgres of its own.
- **Ports, multi-tenant simulation (`docker-compose.multi-tenant.yml`):** entirely separate range — tenant servers `5301`-`5305`, tenant clients `5401`-`5405`, shared Postgres `5540`, tenant-router `5595`, patient-portal server `5590`. Designed to run alongside `docker-compose.yml` without collision.
- **`.claude/launch.json`** has preview configs named `single-tenant-client` and `patient-portal-client` for the Browser-pane preview tool.

## Verification habits worth keeping

Real bugs in this repo were only caught by actually running things, not by reading the code: the JWT claim-remapping issue, a Docker port-rebind race after renaming a compose service, and the migration data-loss issue above. When touching auth, migrations, or the reporting flow, prefer testing against the real running containers (or `dotnet run` + `curl`/a real browser) over trusting a build success alone.
